# Render snapshot and capacity

`WorldState` owns analytic geometry and simulation. `Scene::from_world` copies all supported ordinary spheres, organism node spheres, parent-child capsules, and source markers, preserving stable category/entity/node IDs. It does not truncate at 256. Duplicate IDs and invalid world data are errors. The snapshot is renderer-owned and can be rebuilt after growth or source movement without changing the world.

The GPU record is 64 bytes (`center_kind`, `dimensions`, `color`, `identity`: four 16-byte vectors). WGSL reads a runtime-sized storage array and an explicit active count, bounded again by `arrayLength`. An empty scene allocates one zeroed dummy record but has active count zero. Shader and Rust layouts are checked by tests. The buffer is reused when the snapshot's packed data is unchanged and reallocated only when capacity must grow; its current capacity may exceed the active record bytes. Snapshot construction and CPU-to-GPU upload are distinct operations.

`GpuRenderer::new` defaults to a 16 MiB primitive-storage budget. `with_primitive_budget` accepts a smaller or larger explicit budget of at least one record. The effective ceiling is the minimum of that budget, `max_storage_buffer_binding_size`, and `max_buffer_size`. Checked arithmetic precedes allocation; a scene above the ceiling returns `PrimitiveCapacity { requested_bytes, allowed_bytes }`. Allocation failures return `Gpu`. Neither error mutates `WorldState`. The budget covers primitive storage only; render textures, query buffers, other allocations, and driver overhead are additional. Device limits are ceilings, not a memory availability promise.

Direct GPU traversal still tests every active primitive for every primary pixel ray. Automatic drawing uses direct traversal for at most four primitives and attempts the derived GPU BVH above that size. `query` remains direct by default. Both paths keep the nearest analytic hit and read its color by the winning primitive index; equal-distance hits retain insertion order. A packed-geometry change triggers a full BVH rebuild; identical data and camera-only changes reuse it. GPU BVH allocation is separately bounded by the same configured byte budget and adapter limits. Automatic BVH preparation capacity/allocation failure falls back to direct; an explicit BVH request returns an error. No camera culling is performed. See the [CPU/GPU contract](cpu-gpu-contract.md) and [acceleration research](../architecture/spatial-acceleration.md).
